# ADR-0004：音频播放走「主进程本机代理」而不是把直链交给渲染进程

- 状态：已采纳（M2 落地并实测）
- 日期：M2 期间
- 相关：`apps/desktop/src/main/media-server.ts`、`apps/desktop/src/main/services.ts` 的 `resolveForPlayback()`、`apps/renderer/src/lib/audio-engine.ts`、`docs/PLAN.md` §2.5

## 背景

播放要同时满足四条互相拉扯的约束：

1. **网易云 CDN 的音频直链不是「随便 GET 就能拿到字节」的**：需要 `Referer: https://music.163.com/`，部分资源还要带账号 cookie（`MUSIC_U`）。而 `<audio src="...">` 由浏览器内核发起请求，**我们无法为它附加任何自定义请求头**。
2. **渲染进程绝不能碰凭据**（PLAN §2.5 的账号安全红线）：cookie 只允许留在主进程。
3. **必须支持 `Range`**：一首无损 FLAC 普遍 30~50MB（实测 47288571 / 54733446 / 52363920 字节），拖动进度条、跳播都要靠 HTTP Range 分段取，不能整首下完再放。
4. **直链会过期**：`/song/url/v1` 返回的地址带时间戳签名，几十分钟后失效；渲染进程不应感知、也不应缓存它。

## 备选方案

### A. 渲染进程直接把上游直链塞进 `<audio src>`
- 否决：`<audio>` 发不出 `Referer`，网易云 CDN 大概率 403；要让它能取到就得把 cookie 交给渲染进程或塞进 URL，直接违反红线 2；直链还会出现在渲染进程的内存/DOM 里，任何 XSS 都能顺走。

### B. 主进程把整首音频拉成字节流，再通过 IPC 交给渲染进程播放
- 否决：一首歌 30~50MB 全量缓冲，首次出声要等到（或至少缓冲一大截）才有声音，内存翻倍；`Blob` 播放还会丢掉 Range 语义，拖动进度条要么重下要么全在内存里。IPC 也不适合传流。

### C. 主进程起一个只监听 `127.0.0.1` 的 HTTP 代理，`<audio>` 指向它（**采纳**）
- 采纳理由：把「带凭据、带 Range 的请求」留在主进程，只把一个**不透明地址**交给渲染进程；`Range` 天然透传；直链与 cookie 都不出现在渲染进程里。

## 决策

1. **`MediaServer`（`apps/desktop/src/main/media-server.ts`）**
   - 只 `listen(port, '127.0.0.1')`；端口默认 `0`（由内核分配随机空闲端口），排障可用 `PI_MEDIA_PORT` 固定。
   - 启动时生成随机 `token = randomBytes(16).toString('hex')`，地址形如 `http://127.0.0.1:<port>/audio/<mediaKey>?t=<token>`。
   - 三重校验：非环回来源直接 403、token 不符 403、路径不匹配 `^/audio/[A-Za-z0-9_-]{8,64}$` 404。
   - `mediaKey` 是**我们自己生成的 UUID**，不是上游 URL——上游地址只存在于主进程内存里。
   - 转发时透传客户端的 `Range`，并把上游的 `content-range` / `content-length` / `accept-ranges` / `content-type` 等原样回写；客户端断开即 `destroy()` + `abort()` 上游请求（不留下悬挂的连接）。
2. **解析与凭据都在主进程**：`Services.resolveForPlayback(song, level?)` 决定音质（`clampQuality(preferredQuality, capability.maxQuality)`）→ 走 `ResolverChain`（M2 只有官方源 `wy`）→ 用 `Range: bytes=0-65535` 探针做**字节嗅探**（`content-type` 不可信，实测网易云对 FLAC 返回的是 `audio/mpeg`）→ 结果 TTL 缓存 5 分钟，再注册成 `mediaKey` 返回 `src`。
3. **渲染进程只认 `src`**：`lib/audio-engine.ts` 里的单例 `<audio>` 直接 `element.src = src`，不解析、不拼接、不缓存上游地址；同时把元素挂到 `window.__piAudio`，只为让主进程的 UI 冒烟能读到播放状态（`currentTime` / `paused` / `readyState` / `currentSrc`）。

## 后果

- 正向：渲染进程零凭据、零直链；Range 拖动可用；上游地址换新对 UI 完全透明；以后 L3（LX 插件）的网络也能复用这条通道，便于审计与限流。
- 代价：多了一个本机 HTTP 服务需要随应用生命周期启动/关闭（`Services.init()` 启动、`dispose()` 关闭），并要自己兜住异常路径（解析未命中 404、上游非 2xx/206 一律 502）。
- 已知边界：代理只对环回地址开放，因此**同一台机器上的其他进程也能连**——token 是这里的唯一门槛，不要把它打日志到用户可见处（当前只在排障日志里出现）。
- 失败信息要翻译：渲染进程拿到的只有「404 / 502」，`state/player.ts` 负责把它们变成「这首歌没有可播放的音源」这类人话，而不是把状态码丢给用户。

## 复审触发条件

- Electron / Chromium 提供了「可为 `<audio>` 指定请求头」或主进程直接推流（MSE）的稳定能力；
- 播放不再依赖网易云 CDN（例如全部改成自有音源或本地文件）；
- 需要支持边下边播（M5 下载）且证明代理是瓶颈。
