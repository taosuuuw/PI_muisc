```
components/RhineLayer.tsx        React 宿主：三层界面（DOM 浮层）+ 数据接线 + Esc 钩子
  └─ src/rhine/
     ├─ rhine-constants.ts       几何 / 相机 / 光照 / 交互的常数（每条标 SOURCE）
     ├─ rhine-motion.ts          纯运动学：波浪、弹簧、惯性、取景（+ 17 条单测）
     ├─ rhine-input.ts           自由平面拖拽 + 滚轮累计器（不碰 DOM）
     ├─ rhine-quality.ts         画质四档 + 渲染尺寸（像素预算 8.3MP / 纹理上限）
     ├─ rhine-case.ts            程序化 CD 盒：几何 + 材质 + 图集采样 + 清晰度
     ├─ rhine-cover-atlas.ts     封面图集：一张 2048² 纹理 + 实例 UV + LRU 槽位
     └─ rhine-scene.ts           场景主体：阵列、波浪场、抽取、相机、光照、后期、输入
```

**数据映射**：列 = 歌单（`useMyPlaylists` / `usePersonalizedPlaylists`，收藏档按 `subscribed` 过滤、
剔掉 `specialType=5`）；行 = 曲目（`library:playlist-tracks`，首批 200 首，未加载的位置挂「歌单封面 +
序号」的占位卡）；队列档（环形菜单的「播放列表」）是一列特殊内容，直接进放大档。

**三层界面**：`overview`（总览 / 列名牌）→ `near`（近景 / 右侧详情栏）→ `detail`（放大 / 完整曲目单）。
层级是这一层自己走的（同一台相机的连续运动），宿主管的是「现在在浏览哪一路歌单 / 有没有在看队列」。

**接线**：`App.tsx` 在 `uiStyle==='avant' && avantStyle==='rhine'` 时渲染这一层，并让
`PlaylistCoverflowOverlay` 与歌单/队列那两档 `SongListOverlay` 让位；根节点写
`.pi-app[data-avant-style]`。入口与别的功能一样走**小球手势**：空白处按住出 `PI` 键 → 上划六块按键卡
→ 「我的歌单 / 收藏歌单 / 推荐歌单」。

### 六之负六、换歌时的波浪（2026-10-21，已修）

主人原话：「滚轮滚动切换歌曲时，没有波浪涌动式的过渡动画」（附录屏 `1792606373422.mp4`）。

**两个原因叠在一起**：

1. 第四轮为了突出选中那张，把**涟漪**也乘了 `waveMask` —— 焦点列的涟漪只剩 34%，
   换歌时那列只抖 1/3，肉眼就是「没动」。涟漪是换歌这一下的瞬时响应，本不该被峰形遮罩压。
2. 第六轮为了「挑歌时镜头不切换」，把焦点列的**行滑动也冻住了** —— 而整列滑动正是「涌动」的主要来源。

**修法**：涟漪不再乘 `waveMask`；焦点列恢复滑动；**镜头与盒子仍然钉在锚点上**（第六轮的诉求不变）。
也就是「相机取景不动，但阵列照常流动」。

新增验收第 ⑱ 条直接量涟漪：换歌后连采 1.4 秒，邻行台面起伏幅度要求 ≥0.3 世界单位（盒高 3.35）。

### 六之负五、卡死根因（2026-10-21，看门狗实抓，已修）

**证据**（`%APPDATA%\pi
hine-watchdog.log`，看门狗 `Debugger.pause` + `Profiler.stop`）：

```
at t :7282:12021
at Dge.copyTextureToTexture :7333:51356
at commit :8141:16635
at tick :8148:16106

热点（2ms 采样）：getParameter 6737 次 ≈ 13.5 秒 / drawImage 1784 / measureText 716
                getBoundingClientRect 706 / updateCamera 517 / slotFor 252 / paintPrinted 226
```

**根因**：`rhine-cover-atlas.ts` 的 `commit()` 对每个待传格子各调一次 `copyTextureToTexture`，
而**每格都会让 `uploadTexture` 整张重传**，于是「N 次全量上传 + N 次 GPU 同步查询」；
卡过一次之后积压不收敛、越滚越多，一帧上百格 = 几十秒，主线程彻底出不来（输入不处理、不提交新帧）。

**修法**：彻底不走逐格 `copyTextureToTexture` —— 只要有格子待传就**整张图集重传一次**
（`texture.needsUpdate`，16MB、几毫秒）。这条路是唯一会调 `copyTextureToTexture` 的地方，拆掉即消失。

### 六之负二、主人第五轮的两条（附证据与一条遡留）

1. **拖动时没有队列移动的动画，直接切到下一组 cd 盒。** 真凶是上一轮我自己埋的：
   `onPointerMove` 用 `clampLane()` 去算拖拽的列位置，而它内部是 `Math.round`——取整了。拖拽时相机是
   1:1 跟手的（`columnCamera.value = dragTrack.lane`），于是手在连续拉、镜头却一帧跳一整列。新增 `clampLaneRaw()`

   **1.0 格 → 0.362 格**（一列 = 1 格）。

2. **进去拖动几下或点开曲目单就卡死。** 根因是一个**渲染环**：`catalog` 的 `useMemo` 依赖了

   → `setFocus(新对象)` → 再渲染 → 又是新 `catalog`…… 队列一非空就转起来。两处堵上：`catalog` 传给场景前
   做**签名去重**（列键/曲目数/卡片数/首尾卡片键）、`setFocus` 内容相同时**返回旧引用**让 React
   跳过更新。第 ⑭ 条：播后 1.6 秒仍有 73 帧、场景自报 69.8fps（不再是永久卡死）。

3. **（遡留、已登记不装作已解决）播放那一瞬间的顿挫**：p95 55~105ms、最差 140~310ms。

4. **顺带修的一件事**：`prefers-reduced-motion: reduce` 之前是**一帧到位**（`presence` / `reveal` / `detail` /

   波浪也不再归零（开场波减半、静息呼吸保留）。本机读数是「减少动态效果=关」，所以它**不是**第 1 条的真因，
   但这个坑确实存在，一并填了。

5. **这一轮的教训（记在这里）**：改这份脚本不能用 `Get-Content` + `Set-Content` 整文件重写 ——

### 六之负一、主人第四轮的三条（都已修，附证据）

1. **拖动时画面卡顿。** 三条对症的处理（都留在代码里）：
   · 拖拽/惯性期间**跳过封面烘焙与图集上传**（`tick()` 里那段判断）——新列的歌单封面会成批到达，
     一次 `flush()` 在主线程上画 2048² 画布、再往 GPU 传一块，几次叠在一帧里就是肉眼可见的一顿；
   · 每帧烘焙上限 4 → **1**（`BAKES_PER_FRAME`），积压只在松手后以 1 张/帧消化，不会成爆
     （第一版直接推迟整轮烘焙，结果松手后积压一次性涌入，量到 10 个 34~42ms 的长帧 —— 记在这里）；

3. **滚轮换曲时镜头飘到「歌单选择」的视角、cd 盒没有波浪。**
   · 镜头飘走是第 2 条的另一面（瞄准点错，镜头就一直停在阵列那一侧），同一处修好；
   · 「没有波浪」是我第三轮**削过头**了：那一轮为了突出选中那张，把焦点列的波浪整列关掉，
     主人这一轮的原话是「cd 盒没有正常表现波浪流动式的动画」。现在改成**压到 34%**

### 六之零、主人第三轮的两条（都已修，附证据）

1. **歌曲选择页滚轮换曲时，四周波浪乱浮、选中那张没有明显高出来。**
   量出来的真因有两层：
   · 参考把**电影镜头那一支**的「肩部山丘」（`settlingWave(distance, 26.56) * columnStrength(...)` 整项）
     也放进了交互场（SOURCE: `RhineLabUI src/scene.ts:1378`）。它的包络是

### 六之一、主人第二轮报的两个 bug（都已修，附证据）

1. **拖动过程中 CD 盒队列会忽然消失，松手才回来。**
   真因在**总览档**：横向拖动改变焦点列，而焦点列的行号沿用的是**上一列的**（总览里 = 那一列的
   中点，202 首的列就是第 113 行）；一旦拖到更短的歌单（4~20 首）上，这个行号落在那一列之外，
   `writeInstances()` 的行窗口算出 `rowMin > rowMax`，于是**这一列一个盒子都不画**；松手后
   行号被 `clampRow` 夹回范围，列就「回来了」。
   修法三条（都在 `rhine-scene.ts`）：① 总览档不再把焦点列的行号钉到拖拽行上（每列停在自己中点）；
   ② 行窗口的中点先夹进本列有效范围，`rowMin <= rowMax` 变成恒等式，任何越界行号都只会被夹住；
   ③ 拖拽的 lane / row 与松手惯性都夹到目录边界，镜头不会把整面阵列推出画外。
   冒烟第 ⑭ 条在**拖动过程中**连续采样 32 次、跨过 34/226/610/11/20 五列（含 610 → 11 这种
   「长列 → 短列」），焦点列最小绘制行数 10、场上最小绘制 114 —— 一帧都没空过。
   视觉证据：`docs/m3r36-rhine-drag.png`（拖动中，11 首与 20 首的短列都完整在画）。
2. **歌曲选择页换曲没有「从队列升起」与「被换下来的那张沉回队列」的过渡。**
   第一版只有一张常驻的「抽出来那张」，换选时它的位置直接改坐标（瞬移），`lift` 也一直是 0.4。
   现在照参考补上 `outgoing`（我们叫「归位副本」）：换选瞬间把当前这张留在原地（四层几何与阵列
   共用、封面走单张瓦片 uniform 采样图集），`lift` 归零 ⇒ 新那张从队列里升起（4.2 阻尼，0.76s
   到位），旧那张先转正、再沉回去（`returnStep` + `damp(o.lift, 0, 4.2)`，约 1.8s）；拖回正在
   归位的那一格会把它的高度接回来（参考同款「快速切回保留升降状态」）。选中波也照参考改成
   「新那张升到 0.35 之后再扩散」。
   冒烟第 ⑮ 条读数：换曲后 80ms `lift 0.283 → 0.036`、场上出现 1 张副本（高度 0.295）；
   +1.1s `lift 0.390`；+2.8s `lift 0.400`、副本清零。
   视觉证据：`docs/m3r36-rhine-rise.png`（面板已切到第 10 首，升起的那张带红脊浮在队列之上）。
   补充：参考的 `outgoing` 不设上限，我们加了 `GHOST_LIMIT = 4`（连切太快时最旧的一张立刻归位），
   因为每个副本是一组 Mesh + 一张自己的封面材质，不封顶会堆出几十组。

### 六之二、修这两个 bug 时顺带查出来的第三个 bug

3. **拖过一次之后滚轮失灵，必须再点一下才恢复。**
   修 ② 时冒烟出现「滚轮事件投递到了画布、但档数 = 0」。把判定记进调试面之后一眼看到
   `{"steps":0,"held":true,"level":"near"}` —— `onWheel` 开头有「指针按着就别滚」的守卫，而
   `pointerId` 在拖拽结束后没被清掉：`pointerup` 只要没落到画布上（松手在别的元素、窗口失焦、

   走同一套收尾、`blur` 直接清干净），并顺手把指针 down/up 记账进调试面，将来同类问题一眼可查。

### 六之三、本轮之前就记着的简化与偏差

1. **盒体是程序化的，不是参考的 Blender 模型**。参考的盒子来自 `archive-cassette.glb` /
   音乐版的 `music-cd`，本机没有 Blender，也不打算把它的模型资产搬过来，所以按它公开的尺寸
   用基本体拼了一只（圆角盖板 + 边条 + 两颗紧固件 + 书脊嵌条 + 托盘 + 印刷面）。轮廓与材质语言
   接近，细节（螺钉凹槽、内环、压槽）没有。
2. **封面一开始被盖板压成了暗块（已修）**：第一版把印刷面放在玻璃**内部**
   （`z = CASE_DEPTH/2 - 0.008`），结果 78% 透射 + 背面主光的阴影把整面墙的封面压成深色。
   修法是把印刷面移到盒面**外侧** —— 这也是参考的做法（`scene.ts:488-498`）。排查过程用了三条
   独立证据（分层隐藏对照、图集快照、实例瓦片坐标读数），留在 `.tmp/rhine-{noglass,coveronly,zoom,atlas}.png`。
3. **多了一盏正面印刷光**（参考的档案阵列没有，音乐版有灯带）。理由与出处写在
   `rhine-constants.ts` 的 `PRINT_LIGHT_*` 注释里：它的主光/补光都在阵列背面，而我们这一档
   **在墙上贴了封面**，正面必须有人照。
4. **AO 与景深各自算一遍深度**：参考的 `shared-depth.ts` 让两支 pass 共享一张打包深度图
   （省一遍渲染）。那套依赖 three 的 `_renderOverride` 与 `normalRenderTarget.textures` 内部结构，
   我们改用 three 自带的 `SSAOPass` + `BokehPass` 各自渲染，参数（kernel / radius / min / max /
   maxblur / 光圈曲线）照抄，**代价是多一遍深度**，画质档「性能」可以直接把它们关掉。
5. **实例数加了一道硬上界**（`VISIBLE_ROW_WINDOW = 40` 行/列）：参考按视锥动态算候选，
   行窗口之外的行本来就埋在雾里；加这道上界是为了让实例数与 GPU 开销有确定上界。这不是参考的做法。
6. **没有做「解密」的跑马线**：参考详情里盖板会由上而下变清晰、还叠一条沿对角线合拢的黑线；
   我们只做**盖板清晰度**那一段（`setClarity`：磨砂 `roughness 0.42` → 清透 `0.025`），黑线没做。
7. **相机角度与上一版实现不同**：我按参考文档的 59°/19° 转写；上一轮那套实现看起来是更「平」的
   取景（列读成一根根竖带）。两者都能自圆其说，但主人给的三张参考图我没看到，所以**以文档数值为准**；
   若要那种更平的取景，`CAMERA_YAW_DEG` / `CAMERA_ELEVATION_DEG` 两个常数就能调回去。
8. **本机当前是暗档**：所以主成品图偏暗（参考自己也有暗档配色）。我给亮档单独出了一张对照图；
   若主人想让这一档**永远用亮档**（像参考官网那样），说一声就行（把 `setTheme` 的判据写死即可）。
9. **曲目首批只拉 200 首**：更长的歌单在墙上先挂占位卡（歌单封面 + 序号），右侧曲目单也只列已取到的。
   分页续取没做。
10. **没有做捏合缩放、旋转盒体的限幅外的自由观察、键盘方向键换档**：参考的独立 360° 查看器
    （拆解 / 重组 / 准直）整块没做 —— 那是它的「独立模型查看器」，不属于主人这一轮要的三处界面。
11. **性能数字的边界**：p50/p95 是在本机（144Hz + 硬件加速 + 已登录真实账号、24 列 × 40 行窗口、
    129 个绘制实例）量到的；`--no-sandbox` 下量的，与带沙箱的生产态可能有一点点差别。
    低配机器请用莱茵层右下角的「性能」档（关 AO / 关景深 / 阴影 1024 / 透射减半 / 渲染比例 80%）。
12. **调试接缝保留**：`window.__piRhine / __piRhineAtlas / __piRhineTiles / __piRhineShader /
    __piRhineForceTile / __piRhineCoverColor` 是这次验收长出来的调试接口（与 `window.__piAudio`、
    `window.__piMediaSession` 同一类做法），产品逻辑不读它们；将来要收掉只需删 `RhineLayer` 里那几行。
13. **一次真实的着色器编译失败（已修，值得记）**：日志里出现过
    `[pi/renderer:error] THREE.WebGLProgram: Shader Error 0 - VALIDATE_STATUS false` +
    `0:455: 'vMapUv' : undeclared identifier`。真因是**我自己的调试钩子**：把封面材质的 `map`
    置成 `null` 会去掉 `USE_MAP`，而注入里还写着 `vMapUv = coverTile.xy + …`，
    于是顶点着色器编译不过、`useProgram` 报无效、那一帧的绘制被跳过。修法是把「换纯色」改成
    换一张 4×4 的纯色 `DataTexture`（`USE_MAP` 始终成立）。产品路径本来不触发它，
    但它会污染日志、也可能在别人手改代码时变成真故障 —— 终版日志已经是 **0 条 error**。
    同一轮还顺手把 `PCFSoftShadowMap` 换成 r183 实际生效的 `PCFShadowMap`
    （前者已弃用，three 会打一行 warning 并自动退回；代价是 `shadow.radius` 不再起作用）。
